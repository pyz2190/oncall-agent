# 消息队列积压告警处理方案

## 告警名称
- **告警名**: `MessageQueueBacklog`
- **告警级别**: 严重
- **触发条件**: 消息队列堆积消息数持续5分钟超过10万条，或消费延迟超过10分钟

## 问题描述
消息队列积压指生产速度持续大于消费速度，消息在队列中堆积，可能导致：
- 业务处理延迟，数据时效性下降
- 队列存储压力增大甚至打满
- 下游数据不一致
- 极端情况下消息丢失

## 排查步骤

### 步骤1: 获取当前时间
**工具**: `get_current_time`
**目的**: 确定积压开始的时间，定位变化拐点

### 步骤2: 查询消费者日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 最近30分钟
- **查询条件**: `consumer lag OR rebalance OR consume failed`

**查询示例**:
```
地域: ap-guangzhou
日志主题: application-logs
时间范围: [当前时间-30分钟] 到 [当前时间]
查询语句: (level:ERROR OR level:WARN) AND (consumer OR rebalance OR lag)
```

### 步骤3: 查询队列监控日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `mq-metrics`
- **时间范围**: 与告警时间一致
- **查询条件**: `backlog OR produce_rate OR consume_rate`

### 步骤4: 补充内部处理经验
**工具**: `query_internal_docs`
**目的**: 检索消费者扩容与积压治理的操作手册

## 常见原因分析

### 原因1: 消费者处理能力不足
**特征**:
- 消费速率明显低于生产速率
- 消费者CPU或线程打满
- 单条消息处理耗时长

**处理方案**:
1. 增加消费者实例或并发度
2. 优化单条消息处理逻辑
3. 批量消费/批量提交提升吞吐
4. 必要时引入异步处理

### 原因2: 消费者异常或频繁重平衡
**特征**:
- 日志中大量 rebalance 记录
- 消费者频繁掉线重连
- 消费进度停滞

**处理方案**:
1. 排查消费者崩溃或超时原因
2. 调整心跳与会话超时参数
3. 修复导致消费失败的异常
4. 稳定消费者组成员

### 原因3: 生产端流量突增
**特征**:
- 生产速率短时间陡增
- 上游有批量任务或活动
- 消费端本身正常

**处理方案**:
1. 确认上游突增来源是否合理
2. 临时扩容消费者吸收积压
3. 对非关键消息做降级或限流
4. 评估是否需要扩容队列分区

## 紧急处理措施

### 立即操作（5分钟内）
1. **扩容**: 增加消费者实例/并发快速消化积压
2. **扩分区**: 必要时增加队列分区提升并行度
3. **降级**: 对非核心消息暂时丢弃或旁路

### 短期措施（30分钟内）
1. 定位积压是消费慢还是生产快
2. 针对性扩容或优化
3. 持续观察积压曲线下降

### 长期优化
1. 建立消费延迟与积压监控
2. 容量规划与压测
3. 关键链路与非关键链路分离
4. 引入死信队列处理异常消息

## 验证步骤
1. 确认积压消息数持续下降至正常水位
2. 确认消费延迟回到分钟级以内
3. 确认无大量消费失败日志
4. 观察30分钟确保不再反弹
