# 数据库连接池耗尽告警处理方案

## 告警名称
- **告警名**: `DatabaseConnectionPoolExhausted`
- **告警级别**: 严重
- **触发条件**: 数据库连接池活跃连接数持续3分钟达到上限的95%

## 问题描述
当数据库连接池中的可用连接被耗尽时，新的数据库请求将无法获取连接，可能导致：
- 应用线程阻塞等待连接
- 请求大量超时
- 接口响应缓慢甚至不可用
- 连接泄漏持续恶化形成雪崩

## 排查步骤

### 步骤1: 获取当前时间
**工具**: `get_current_time`
**目的**: 确定告警发生的时间范围，用于后续日志查询

### 步骤2: 查询应用日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 最近30分钟
- **查询条件**: `Connection is not available OR connection timeout OR HikariPool`

**查询示例**:
```
地域: ap-guangzhou
日志主题: application-logs
时间范围: [当前时间-30分钟] 到 [当前时间]
查询语句: (level:ERROR) AND (HikariPool OR "Connection is not available")
```

### 步骤3: 查询数据库监控日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `database-metrics`
- **时间范围**: 与告警时间一致
- **查询条件**: `active_connections OR pool_usage`

### 步骤4: 补充内部处理经验
**工具**: `query_internal_docs`
**目的**: 检索连接池配置与泄漏排查的标准操作手册

## 常见原因分析

### 原因1: 连接泄漏
**特征**:
- 活跃连接数持续单调上升不回落
- 日志中存在未关闭连接的警告
- 重启实例后短时间恢复又复发

**处理方案**:
1. 定位未正确释放连接的代码路径
2. 检查是否缺少 try-with-resources 或 finally 关闭
3. 临时重启实例缓解，但需根治代码
4. 通知开发团队修复连接管理逻辑

### 原因2: 连接池配置过小
**特征**:
- 业务高峰期稳定触发
- 连接全部处于活跃状态
- 数据库本身负载正常

**处理方案**:
1. 评估业务并发量与合理连接数
2. 适当上调连接池最大连接数
3. 同步评估数据库最大连接限制
4. 增加连接获取超时监控

### 原因3: 慢查询占用连接
**特征**:
- 单个连接占用时间过长
- 数据库慢查询日志增多
- 连接释放速度跟不上获取速度

**处理方案**:
1. 查询慢SQL日志定位长事务
2. 优化SQL或增加索引
3. 拆分大事务，缩短连接占用时间
4. 为关键查询设置超时

## 紧急处理措施

### 立即操作（5分钟内）
1. **重启**: 重启连接占用最高的实例释放连接
2. **扩容**: 临时增加实例分摊连接压力
3. **限流**: 对高频接口启用限流，降低连接申请速率

### 短期措施（30分钟内）
1. 分析日志确认是泄漏还是配置不足
2. 调整连接池参数并灰度发布
3. 持续观察活跃连接数曲线

### 长期优化
1. 引入连接泄漏检测（leakDetectionThreshold）
2. 完善连接池监控与告警阈值
3. 定期审查事务边界与连接使用规范
4. 压测验证连接池容量

## 验证步骤
1. 确认活跃连接数回落到安全水位（<70%）
2. 检查接口响应时间恢复正常
3. 确认无新的连接超时错误日志
4. 观察30分钟确保问题不再复现

## 相关告警
- `SlowResponse`: 响应时间过长
- `ServiceUnavailable`: 服务不可用
- `HighCPUUsage`: CPU使用率过高
