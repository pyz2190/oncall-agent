# Pod频繁重启告警处理方案

## 告警名称
- **告警名**: `PodCrashLoopBackOff`
- **告警级别**: 严重
- **触发条件**: 容器在10分钟内重启次数超过5次，或处于 CrashLoopBackOff 状态

## 问题描述
Pod频繁重启（CrashLoopBackOff）指容器启动后很快崩溃并被反复拉起，可能导致：
- 服务实例数不足，承载能力下降
- 请求被路由到未就绪实例而失败
- 滚动发布无法完成
- 故障范围随副本扩散

## 排查步骤

### 步骤1: 获取当前时间
**工具**: `get_current_time`
**目的**: 确定重启高发的时间范围

### 步骤2: 查询容器日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `container-logs`
- **时间范围**: 最近20分钟
- **查询条件**: `CrashLoopBackOff OR OOMKilled OR liveness probe failed OR exit code`

**查询示例**:
```
地域: ap-guangzhou
日志主题: container-logs
时间范围: [当前时间-20分钟] 到 [当前时间]
查询语句: (CrashLoopBackOff OR OOMKilled OR "probe failed") AND pod:*
```

### 步骤3: 查询应用启动日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 与告警时间一致
- **查询条件**: `startup failed OR FATAL OR Exception OR panic`

### 步骤4: 补充内部处理经验
**工具**: `query_internal_docs`
**目的**: 检索容器崩溃排查与回滚的标准流程

## 常见原因分析

### 原因1: 应用启动即崩溃
**特征**:
- 容器退出码非0（如1、137）
- 启动日志中有异常堆栈
- 故障紧随一次发布

**处理方案**:
1. 查看启动日志定位异常
2. 检查配置/环境变量缺失
3. 回滚到上一个稳定版本
4. 修复后重新灰度发布

### 原因2: 内存超限被OOMKilled
**特征**:
- 退出码137，事件中有 OOMKilled
- 内存使用接近 limit
- 重启后内存又快速增长

**处理方案**:
1. 适当上调内存 limit
2. 排查内存泄漏
3. 优化堆内存或GC参数
4. 增加内存使用监控

### 原因3: 健康检查配置不当
**特征**:
- liveness/readiness 探针失败
- 应用实际正常但被判定不健康
- 启动较慢的应用频繁被杀

**处理方案**:
1. 调整探针超时与初始延迟
2. 区分 liveness 与 readiness 语义
3. 为慢启动应用配置 startupProbe
4. 验证探针路径正确

### 原因4: 依赖服务不可用
**特征**:
- 启动时连接数据库/中间件失败
- 日志中有连接拒绝或超时
- 依赖恢复后自动好转

**处理方案**:
1. 确认依赖服务状态
2. 增加启动重试与退避
3. 解耦强依赖，优雅降级
4. 修复依赖后观察恢复

## 紧急处理措施

### 立即操作（5分钟内）
1. **回滚**: 若为发布引起，立即回滚版本
2. **扩副本**: 临时增加健康副本维持容量
3. **隔离**: 将异常Pod下线，避免接收流量

### 短期措施（30分钟内）
1. 根据退出码与日志定位根因
2. 调整配置或回滚并验证
3. 观察重启次数归零

### 长期优化
1. 完善探针与资源配置规范
2. 发布前增加启动自检
3. 强化依赖容错与降级
4. 建立重启次数趋势监控

## 验证步骤
1. 确认Pod进入并稳定保持 Running 状态
2. 确认重启次数不再增长
3. 确认服务副本数与就绪数一致
4. 观察30分钟确保不再崩溃

## 相关告警
- `HighMemoryUsage`: 内存使用率过高
- `ServiceUnavailable`: 服务不可用
- `DatabaseConnectionPoolExhausted`: 数据库连接池耗尽
